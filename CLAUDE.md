## Anki add-on fundamentals

Anki add-ons are Python packages that Anki loads from its `addons21/` profile folder at startup.
Keep these conventions in mind when scaffolding or writing add-on code in this repo:

- **Entry point**: each add-on is a folder containing `__init__.py`, which Anki imports on startup.
  Put setup/hook-registration code here.
- **`manifest.json`**: required for each add-on folder — declares `name`, `package` (must match the
  AnkiWeb numeric ID once published, or a unique string for local-only add-ons), `mod` (unix
  timestamp), and optionally `conflicts`/`min_point_version`/`max_point_version`.
- **`config.json` + `config.md`**: optional default user-configurable settings, editable from
  Anki's Add-ons → Config dialog.
- **`meta.json`**: runtime-generated by Anki (stores per-user config + enabled state) — never
  hand-author or commit this.
- **Hooks, not monkey-patching**: prefer `aqt.gui_hooks` / `anki.hooks` (the typed hook system in
  modern Anki) over overriding functions directly. Check the target Anki version's hook list before
  wiring behavior.
- **UI layer**: `aqt` (PyQt-based Anki desktop UI — dialogs, menus, `mw` the main window singleton)
  vs. **core layer**: `anki` (collection/note/card data model, independent of UI). Add-ons that only
  touch data should avoid importing `aqt` so they stay testable without a running Qt app.
- **Packaging**: a distributable add-on is a `.ankiaddon` file — a zip of the add-on folder's
  contents (not the folder itself) at the zip root, with `manifest.json` included and no
  `__pycache__`/`meta.json`.
- **Local testing**: symlink or copy an add-on folder into the user's Anki `addons21/` directory
  (Windows: `%APPDATA%\Anki2\addons21\`) and restart Anki (Tools → Add-ons → View Files opens that
  folder directly).
- **Multiple add-ons in one repo**: if this repo grows to hold several add-ons, give each its own
  top-level folder with its own `manifest.json`/`__init__.py` — Anki loads each folder as an
  independent add-on.

## Development workflow

- Mỗi add-on sống trong 1 top-level folder riêng (xem "Multiple add-ons in one repo" ở trên) —
  làm việc trên add-on nào thì chỉ đụng vào folder đó, không rò rỉ code dùng chung giữa các
  add-on trừ khi chủ động tách ra một package `shared/` (chưa cần ở quy mô hiện tại).
- Trước khi bắt đầu task mới: `git status` để chắc không có việc dở dang bị đè lên.
- Add-on mới bắt đầu bằng bộ khung tối thiểu: `manifest.json` + `__init__.py`, thêm
  `config.json`/`config.md`/tests khi thực sự cần, không scaffold sẵn structure chưa dùng tới.

## Git workflow

- **Branch naming:** `<type>/<ten-addon>-<mo-ta-ngan>`

  | Prefix | Mục đích |
  |---|---|
  | `feature/` | Add-on mới hoặc tính năng mới trong add-on có sẵn |
  | `fix/` | Sửa lỗi |
  | `refactor/` | Refactor, không đổi behavior |
  | `chore/` | Việc lặt vặt (deps, tooling) |
  | `docs/` | Tài liệu |
  | `test/` | Thêm/sửa test |

  Ví dụ: `feature/deck-stats-heatmap`, `fix/card-color-crash-on-empty-deck`.

- **Commit message:** `<type>(<ten-addon>): <mô tả ngắn>` — `<scope>` là tên folder add-on, không
  phải tên file. Ví dụ: `feat(card-color): add config option for tag-based colors`.
- **Không tự động `git commit`/`git push`.** Luôn đề xuất commit message trong code block và chờ
  xác nhận, trừ khi được yêu cầu tự thực hiện.
- `main` luôn ở trạng thái add-on nào cũng load được — không commit code add-on đang dở dang gây
  crash khi Anki khởi động.

## Code quality standards

- Type hint cho public function/method.
- Không dùng `print()` cho debug — dùng `logging`, hoặc `aqt.utils.showInfo`/`tooltip` cho message
  hiển thị cho user.
- Add-on chỉ xử lý data (không import `aqt`) phải giữ được tính chất đó — nếu thấy `import aqt`
  lọt vào module thuần logic, đó là dấu hiệu cần tách lại boundary.
- Giữ file gọn — quá ~300 dòng thì cân nhắc tách theo trách nhiệm (vd `ui.py`, `hooks.py`,
  `logic.py`).

## Testing standards

- Test bằng `pytest`. Phần logic thuần Python (không đụng Qt) test trực tiếp, không cần mock.
- Phần đụng `aqt`/`mw` (main window) cần mock lại vì không có Anki thật chạy trong CI/local test.
- Vị trí test: `<addon>/tests/` bên trong từng add-on — chốt cụ thể hơn khi add-on đầu tiên có
  test thật.

## Communication style

- Trả lời, giải thích bằng tiếng Việt; code, comment, commit message bằng tiếng Anh.
- Ngắn gọn, không rào đón kiểu "Great question!".
- Khi không chắc (đặc biệt Anki API/hook đổi giữa các version) → nói rõ cần verify (đọc
  changelog Anki, hoặc kiểm tra `aqt`/`anki` package đang cài), không đoán mò.

## Anti-patterns

1. ❌ Monkey-patch function khi đã có hook tương đương trong `aqt.gui_hooks`/`anki.hooks`.
2. ❌ Commit `meta.json` hoặc file `.ankiaddon` (build artifact) — cả hai đã nằm trong `.gitignore`.
3. ❌ Tự ý `git commit`/`git push` mà chưa được xác nhận.
4. ❌ Import `aqt` vào module chỉ xử lý data — phá tính testable-without-Qt.
5. ❌ Scaffold structure/tooling cho tính năng chưa cần (vd setup test framework khi add-on chưa
   có logic gì đáng test).
